# 工作流程

## 五個階段

依序進行：探索 → 計畫 → 實作 → 驗證 → 回報。第 2 步只在條件成立時才需要，其他步驟不能省。

1. 探索：動手前先讀相關程式碼、設定檔和現有測試。
2. 計畫：符合下列任一條件時，先列計畫，等使用者確認再動手：
   - 會改超過 3 個檔案
   - 新增或移動資料夾層級
   - 改模組之間的相依方向
   - 更換框架、狀態管理方式或資料庫
3. 實作：照計畫做；計畫要變更時先回報再改。
4. 驗證：照「測試與驗證」的完成定義逐項檢查。
5. 回報：照「溝通規範」的回報範本，一定要寫改了哪些檔案、怎麼驗證、還有什麼沒做。

## 最小改動

- 只改任務需要的檔案和程式碼；不順手重構、不改既有格式或縮排。
- 看到任務外的問題，列在回報的「還沒做」裡，不直接改。

## 什麼時候先問、什麼時候直接做

直接做：可逆且需求明確的改動。

先問，等確認：
- 改公開 API 或函式簽章
- 新增或升級相依套件
- 改資料結構、資料庫 schema
- 需求有兩種以上合理解讀
- 破壞性操作（刪除、覆寫、force、migration），清單見「安全」

## 卡住時

- 同一個問題試了兩種方法都失敗，就停下來回報：試了什麼、各自的結果、你的推測。
- 不要第三次換方法亂試。

## 上下文管理

- 預估超過 30 分鐘或超過 10 個步驟的任務，拆成幾段，每段結束時回報一次。
- 要讀超過 10 個檔案才能回答的搜尋，交給子代理（subagent），只把結論帶回來。
- 同一個問題在對話裡失敗 2 次後，建議使用者開新對話，並附上一段交接摘要。
